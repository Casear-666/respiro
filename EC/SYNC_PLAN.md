# 桌面离线与云端统一日历实施计划

## 范围与已确认决定

- 桌面端保持离线可用；登录后自动与服务器同步日程。
- 网页端在线访问同一账号的日历，暂不实现网页离线缓存。
- 沿用 Electron / React / Node.js / SQLite，不引入完整 CRDT 或更换数据库。
- 同一日程发生并发修改或删除/修改冲突时，保存双方版本，提供使用本地版本、使用云端版本、保留两份（适用时）。
- 日历外观偏好保持各端独立。本次同步对象是日程，包括完成状态、时间、分类和备注。
- 用户已授权把所需服务端变更直接部署到 `aliyun`。部署前停止日历服务并备份完整数据目录及旧程序，验证后恢复运行。
- 继续使用现有 `127.0.0.1:3001` / SSH 通道，不变更其他服务、防火墙或公网入口。

## 1. 持久化与协议

- 数据库升级至 schema 2；保留现有日程及设置，并为已有日程初始化版本。
- 每个服务端日历有永久的随机 `epoch` 和递增 revision。
- `sync_events` 保存每个日程最新的 revision / payload；payload 为 null 表示删除。首版不清理删除记录。
- SQLite 触发器对 events 的实际 INSERT / UPDATE / DELETE 分配 revision，覆盖网页保存、同步写入、导入等入口。无变化的保存不产生版本。
- `sync_receipts` 保存操作 ID、规范化请求摘要和结果。相同操作重试返回原结果；同一 ID 搭配不同内容拒绝。
- `sync_conflicts` 持久保存冲突提交的完整版本；正常日历继续使用云端当前版本。冲突不影响其他日程同步。
- 每个桌面账号副本有 remote shadow、pending 和 inflight 表。本地日程与 pending 在同一事务写入。
- 待上传记录按日程合并；发出前转为不可变 inflight。断网或进程退出后先重放 inflight，不能为不确定是否成功的请求换新 ID。

协议（新增）：

```text
GET  /api/sync/changes?since=0&epoch=...
POST /api/sync/push
GET  /api/sync/conflicts
POST /api/sync/resolve
```

```js
// 每页最多 100 个最新日程状态，按 revision 排序。
// hasMore 时 cursor 为本页最后 revision，否则为事务内读到的当前 head。
{ epoch, cursor, hasMore, changes: [{ id, revision, event /* object | null */ }] }

// 上传不会推进客户端拉取游标，避免漏掉其他设备的变化。
{ epoch, operations: [{ opId, id, baseRevision, event /* object | null */ }] }
{ results: [{ opId, id, status /* accepted | conflict */, revision, event, conflictId? }] }

// 冲突列表使用云端最新状态进行对比。
{ conflicts: [{ id, eventId, localEvent, remoteEvent, remoteRevision, createdAt }] }

// 明确选择；expectedRevision 防止选择期间又发生变化。
{ epoch, opId, conflictId, choice /* local | remote | both */, expectedRevision }
```

约束：

- 验证完整批次后再事务提交；拒绝非法 ID、版本、重复日程、超限批次和无效日程。
- baseRevision 不匹配且内容不同则保留冲突，不覆盖云端。内容完全相同可确认成功。
- 游标超出服务端 head 或 epoch 不匹配返回明确错误，保留本地未上传内容，不自动清库。
- 不依赖电脑的本地时间来决定覆盖顺序。
- 沿用现有身份验证、请求来源校验、请求体上限和用户隔离。

## 2. 桌面同步与账号

- Electron 主进程负责网络访问和会话；渲染进程仅能使用受限 IPC。
- 登录使用现有 HttpOnly 会话接口，主进程管理 Cookie；不把会话或口令暴露给页面。
- 仅允许 HTTPS 或 loopback HTTP 服务地址；禁止携带用户名、密码、查询参数和重定向。
- 会话用 Electron safeStorage 加密后保存，不保存密码；无法安全保存时要求下次重新登录，但保留离线数据。
- 未登录的本地日历仍为原 `calendar.sqlite`。
- 账号副本使用 `profiles/<SHA256(origin + userId)>/calendar.sqlite`，与其他账号及本地空间隔离。
- 初次登录提供“仅使用云端日历”和“合并本地日程”选择；合并前保存本地备份，合并不删除原本地空间。再次登录已有账号副本不重复导入。
- 退出登录撤销/清除会话并返回本地空间；账号副本及待同步修改保留在独立目录，重新登录原账号后继续。
- 同步在启动、登录、修改后短暂防抖、恢复网络、窗口恢复焦点和定时轮询时触发；同一账号只运行一个同步任务。
- 请求含超时，失败保留队列并退避重试。401 显示重新登录，离线编辑不受影响。
- 关闭软件只等待本地持久化，不等待联网。切换账号前排空页面保存队列并停止旧账号任务，旧响应不能写入新账号。

## 3. 网页与界面接入

- 网页保存改用同一版本协议；旧版无版本写入接口拒绝危险写入并提示刷新。
- 网页列表读取保留对应版本；失败重试复用操作 ID，冲突在服务端保存。
- 网页定时/恢复焦点拉取变化，操作、编辑弹窗和未保存内容存在时不覆盖当前视图。
- 桌面显示本地保存状态与云同步状态；设置中提供服务器地址、登录、立即同步、退出和冲突处理。
- 冲突对比展示标题、开始/结束时间、分类、完成状态、备注及删除状态。
- 远端刷新与本地保存串行化；仅在没有新编辑时替换页面快照。刷新后清空旧撤销历史，防止撤销恢复陈旧远端数据。
- 初次连接、切换账号和冲突解决均使用现有 Dialog / 设置样式；不新增网页离线机制。

## 4. 验证条件

存储和 HTTP：

- schema 1 日程原样保留并能增量拉取；删除产生墓碑；无变化不增版本。
- 分页之间发生并发更新仍不会永久遗漏；无效游标和 epoch 拒绝。
- 重复 push（包括服务器成功但客户端未收到响应）只应用一次。
- 混合合法/非法批次整体回滚；同一 opId 更换内容拒绝。
- 两个账号使用同样 event ID 仍完全隔离。
- 同时修改、删除/修改冲突保存双方数据；解决冲突前再次远端修改会重新提示。
- 网页导入产生同步变化；旧版无版本写入不能静默覆盖。

桌面和界面：

- 离线增删改、退出重开后 pending / inflight 均保留，联网后收敛。
- 请求在途期间继续修改同一日程，回执不能清除新修改。
- 账号切换、401、断网和失败重试不会混账号或丢失数据。
- 云端变化到达时页面未保存编辑、编辑器草稿和示例空间不被覆盖。
- 首次合并前备份，重新登录不重复导入。
- 真实 HTTP + 两个本地 SQLite 副本验证两端往返及删除。
- 生产构建、桌面冒烟、Windows 安装包通过。现有已知 OOM 的悬停测试不作为本次门禁。
